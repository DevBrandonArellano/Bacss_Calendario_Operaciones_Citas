# Roadmap, MVP y decisiones clave

## MVP recomendado

El MVP mínimo viable para validar el negocio con un solo tipo de cliente (p. ej. un taller) cubre las Fases 2 a 5 más notificaciones básicas:

1. Core multitenant + auth + RBAC (Fase 2).
2. Clientes (Fase 3).
3. Servicios y profesionales (Fase 4).
4. Agenda, disponibilidad y citas — el corazón del producto (Fase 5).
5. Notificaciones por email (subconjunto de Fase 6: solo recordatorios básicos).

Con esto ya es posible operar la agenda de una empresa real de un solo rubro. Pagos, módulos especializados, documentos/tareas transversales, reportes y API pública son valiosos pero no bloquean la validación inicial del negocio.

## Funciones de 2ª etapa

- Pagos con pasarela real (más allá del registro simple de la Fase 7).
- WhatsApp/SMS reales (Fase 6 los deja preparados con stubs, integración real es 2ª etapa).
- Módulos especializados adicionales más allá de los 4 iniciales.
- Suscripciones/planes comerciales con cobro automático (Fase 14 solo prepara la arquitectura).
- App móvil nativa (React Native), reutilizando el mismo backend API-first.
- Migración a schema-per-tenant si el volumen o un cliente regulado lo exige (ver ADR-001).
- MFA en autenticación.

## Riesgos técnicos

| Riesgo | Impacto | Mitigación |
|---|---|---|
| Fuga de datos entre tenants por bug de aplicación | Alto (crítico para el negocio) | Managers tenant-aware por defecto, middleware de resolución de tenant, tests de aislamiento en cada fase + auditoría dedicada (Fase 13) |
| Doble reserva bajo concurrencia | Alto (rompe confianza del producto) | Locking pesimista + constraint de exclusión en base de datos (`docs/booking-engine.md`), test de concurrencia explícito |
| Alcance de módulos crece sin control (feature creep por rubro) | Medio | Disciplina de "una fase a la vez", módulos aislados y con interfaz mínima hacia el core |
| Datos sensibles de laboratorio/legal expuestos por permisos laxos | Alto (legal/reputacional) | RBAC reforzado + auditoría de lectura en esos módulos, revisión dedicada en Fase 13 |
| Esquema compartido se vuelve cuello de botella con muchos tenants grandes | Medio (a mediano plazo) | Ruta de migración a schema-per-tenant documentada desde el ADR-001, no es una sorpresa arquitectónica |
| Deriva entre API interna y pública (duplicación de lógica de negocio) | Medio | Ambas superficies reutilizan los mismos casos de uso/servicios (Fase 12B) |

## Decisiones arquitectónicas clave (resumen)

- Django + DRF + PostgreSQL + React, por velocidad de desarrollo y madurez del ecosistema (ADR-000).
- Esquema compartido con `organization_id` para el MVP, con ruta de migración a schema-per-tenant (ADR-001).
- Dos superficies de API completamente separadas: interna (frontend propio) y pública versionada (terceros).
- Motores de disponibilidad y reservas como componentes puros, independientes de la UI y del canal de entrada.
- Módulos especializados aislados entre sí, activables por organización sin migraciones dinámicas de esquema.
- Estándares transversales (logging RFC 5424, manejo de errores uniforme, ISO 25010/27001, TDD/ISTQB) definidos desde la Fase 1 para que cada fase posterior los aplique sin tener que re-decidirlos.
